# refactoring skill

## このスキルが目指すゴール

`app/` 配下の既存コードを **SOLID / KISS / DRY と SQuaRE シリーズ品質モデル** の観点でレビューし、**優先度付きの指摘レポートを標準出力に出す**。

レポートを読んだユーザーが「仕様書化してほしい」と希望した場合のみ、後続で **リファクタリング仕様書** を `app/specs/<feature-name>/` 配下に生成する。仕様書のフォーマットと配置は [[updating]] の流儀を踏襲する（リファクタリングは「既存システムへの修正」の一種だから）。

> **このスキルはコードを書き換えない**。レビュー結果の出力と、希望時の仕様書生成までが責務。実コードへの反映は、生成した仕様書を起点に [[spec-implementing]] で行う。

## 想定ユーザー

- ビジネスパーソン、または初学者エンジニア
- SOLID / KISS / DRY / SQuaRE といった用語に馴染みがない可能性がある
- 専門用語の初出時は **1 行で噛み砕いて補足** する（例: 「SRP（単一責任原則=1つのクラスは1つの責務だけ持つべき）」）
- 「なぜこれが問題なのか」「直さないとどう困るか」を平易な言葉で添える

## 起動トリガー

ユーザー発話に以下のようなキーワードが含まれるとき:

- 「リファクタリングして」「リファクタリング案を出して」
- 「コードを見直して」「コードレビューして」
- 「品質チェックして」「設計をチェックして」
- 「SOLID 違反がないか見て」「DRY 違反がないか見て」
- 「SQuaRE の観点でレビューして」「保守性チェックして」

逆に、機能追加・バグ修正・新規実装の依頼では発動しない（それぞれ [[updating]] / [[spec-writing]] が担う）。

## 絶対に守る制約

### 1. コードを直接書き換えない
- 本スキルの責務は **レビュー（レポート出力）** と **希望時の仕様書生成** まで
- `app/src/` 配下のコード編集・依存パッケージ追加・テスト実行などの実装行為は行わない
- 実装は仕様書を起点に [[spec-implementing]] で行う

### 2. 振る舞いを変える提案をしない
- リファクタリングは **外部から見た振る舞いを変えずに内部構造を改善する** 活動
- バグ修正・機能追加・仕様変更を兼ねた提案は **本スキルのスコープ外**（必要なら [[updating]] を案内）
- 「ついでにこれも直したい」と感じても、振る舞いが変わるなら別タスクに切り分ける

### 3. 既存テストの維持を前提に提案する
- レビュー提案は **既存テストが通り続けることを前提** に組み立てる
- 提案を採用したら既存テストが落ちる、というケースが想定されるなら、その旨と「テストを直す必要があるか / 仕様を見直す必要があるか」を明記する
- 既存テストが赤い状態でレビューする場合は、レポート冒頭でその事実を強調し「先にテスト失敗の修正を提案する」旨を書く

### 4. 既存の技術スタックを尊重する
- **Hono 単体構成 (TypeScript) を崩す提案をしない**（React / Next.js / Vue 等の導入を提案しない）
- スタイリングは Tailwind CSS (CDN版) を踏襲
- データストアは既存のものを尊重（変更を伴うならユーザー確認を推奨と明記）
- `.kiro/steering/code-conventions.md` のコーディング規約に沿った提案にする（`any` 禁止、`enum` 禁止、戻り値型明示など）

### 5. 過剰設計を避ける（KISS の自己適用）
- 「将来こうなるかも」「拡張性のため」だけの抽象化導入を提案しない
- 3 箇所同じパターンが出るまでは抽象化しないのを目安にする
- 指摘は **「現状で起きている / 起きそうな具体的な困りごと」** を根拠にする

### 6. パッケージマネージャ
- コマンド例は `npm` を標準とする（`npm test` / `npm run lint` など）
- **ローカルツール（biome / vitest）は `npx` で呼ばず `package.json` の script 経由で呼ぶ**（`npx` は未検出時にレジストリから別バージョンを取得して実行してしまう）

## レビュー観点

### A. SOLID 原則

| 略 | 名称 | 平易な言い方 | 主なチェック |
| --- | --- | --- | --- |
| S | 単一責任原則 | 1ファイル / 1関数は1つの責務だけ | 1ファイルが複数の役割を抱えていないか / 関数が長すぎないか（50行目安） |
| O | 開放閉鎖原則 | 拡張に開き、修正に閉じる | 機能追加のたびに同じ巨大 switch / if を毎回触る構造になっていないか |
| L | リスコフ置換原則 | サブタイプは基底型と差し替え可能 | 継承先で例外を投げる / 引数を狭めるなど契約違反がないか |
| I | インターフェース分離原則 | 太い1つより、細い複数 | 「使わない関数」を必須実装に強いる型がないか |
| D | 依存性逆転原則 | 上位は抽象に依存 | ルートから直接ファイル I/O / DB を叩いていないか（lib への切り出し漏れ） |

> Hono 単体構成では極端な OOP は使わないので、S / D を中心に見る。L / I は型レベルの違和感を拾う程度でよい。

### B. KISS / DRY

| 観点 | チェック |
| --- | --- |
| KISS | ネストが深すぎる（早期 return で平坦化できるか）/ 一発で読める命名か / 過剰な抽象化を入れていないか |
| DRY | コピペコードの塊（3 箇所以上）/ 同じバリデーション・整形ロジックが散らばっていないか / マジックナンバー・リテラルの重複 |

### C. SQuaRE シリーズ品質モデル（ISO/IEC 25010）

リファクタリングが最も寄与する **保守性** を中心に見つつ、明らかな問題があれば他カテゴリも拾う:

| カテゴリ | サブ特性 | チェック例 |
| --- | --- | --- |
| **保守性** | モジュール性 | 1ファイルに無関係な機能が同居していないか |
| | 再利用性 | 純粋ロジックが `lib/` に切り出されているか（routes に張り付いていないか） |
| | 解析性 | 命名・型がコードの意図を語っているか / コメントが「なぜ」を説明しているか |
| | 修正性 | 1つの仕様変更で複数ファイルを連鎖修正する構造になっていないか |
| | 試験性 | テストしやすい単位に分かれているか / 副作用が引数で注入できるか |
| 信頼性 | 障害許容性 | 外部入力・I/O 失敗時のエラー処理に抜けがないか |
| | 回復性 | リトライ・ロールバック観点（過剰でない範囲で） |
| セキュリティ | 機密性・完全性 | 入力バリデーション漏れ / シークレットの混入 / 既存防御の不用意な弱体化 |
| 性能効率性 | 時間効率性 | 明らかな O(n²) / 不要なループ・I/O / N+1 クエリ等 |
| 使用性 | 学習容易性 | API / 画面の挙動が直感に反していないか（広義の保守性として軽く拾う） |

> 機能適合性・互換性・移植性は通常リファクタリングのスコープ外。明確な問題が見つかったときだけ拾う。

### D. プロジェクト固有の規約準拠

- TypeScript: `any` / Non-null assertion (`!`) / `@ts-ignore` / `enum` の使用がないか
- export 関数の戻り値型が明示されているか
- 外部入力（HTTP / env / 外部 API）が Zod で検証されているか
- ディレクトリ構成（`routes/` / `lib/` / `schemas/` / `components/` / `middleware/` / `types/`）から逸脱していないか
- 命名規則（ファイル: kebab-case / 変数: camelCase / 型: PascalCase / 定数: UPPER_SNAKE_CASE）
- テストが `tests/` 配下に `src/` と対応する階層で配置されているか

## 対話フロー

### Step 0: レビュー対象の特定

引数指定があれば最優先で採用する（`refactoring app/src/routes/expense.ts` のように渡される想定）。

引数がない場合は **必ず `AskUserQuestion` で対象を選ばせる**:

- (A) 直近の作業で変更したファイル（会話の文脈やファイル更新日時から推定して提示する）
- (B) 特定のファイル / ディレクトリ（パスを尋ねる）
- (C) `app/src/` 全体
- (D) 特定機能（`app/specs/<feature-name>/` 配下に対応する既存 feature を選ぶ → 関連ファイルを推定）

> 候補が1件だけ確定していても、自動で進めない。リファクタリングは影響範囲が読みづらいので、必ず明示同意を取る。

### Step 1: ベースライン情報の収集

レビュー精度を上げるために、以下を **読み取り専用** で収集する:

1. ルート `AGENTS.md` / `.kiro/steering/code-conventions.md` / `.kiro/steering/testing-unit-patterns.md` を `Read` で再確認
2. 対象ファイルを `Read` で読む（必要に応じて `Grep` で呼び出し元も確認）
3. 関連する既存テストの有無を `Bash` (`ls` / `find`) で確認
4. 必要なら `Agent` (subagent_type=Explore) で広めに関連箇所を探索
5. **テストの現状確認**（任意・推奨）: ユーザーに確認を取ってから `npm test` を実行し、現状の緑/赤を把握
   - `npm` はグローバルではなく **runtime 配下**（`runtime/node/bin`、Windows は `runtime\node`）のものを使う。実行時に PATH へ runtime の bin を付与する（例: `app/` 配下で `PATH="$PWD/../runtime/node/bin:$PATH" npm test` / Windows は `$env:Path = "$PWD\..\runtime\node;$env:Path"; npm.cmd test`）。**Windows では `npm` / `npx` を裸で書かず `npm.cmd` / `npx.cmd` とする**（裸だと `npm.ps1` に解決され ExecutionPolicy で失敗する）。詳細は [AGENTS.md](../../../AGENTS.md) の「実行環境（Node.js / npm / npx）」を参照

> 既存テストが赤い場合、レポート冒頭でその事実を強調する。リファクタリング提案は「テスト緑」を前提に組むため、まず赤を直すべき旨を書く。

### Step 2: レビュー実施と指摘の優先度付け

収集した情報をもとに、上記「レビュー観点」A〜D の順で観点漏れがないか確認しながら指摘を作る。

各指摘には **以下の要素** を必ず含める:

- **No.**（連番）
- **観点**（SOLID-S / KISS / DRY / SQuaRE-保守性-モジュール性 / 規約準拠 など、複数該当なら主要なものを1つ + 関連も列挙）
- **対象**: ファイルパス + 行番号レンジ（`app/src/routes/expense.ts:42-78` 形式）
- **現状**: 何がそうなっているか（事実を 1〜3 行で）
- **問題**: なぜこれが問題か（**初学者にも分かる言葉で**）
- **リファクタリング案**: どう変えるか（必要なら短いコード断片で示す。実コードは書き換えない）
- **影響範囲**: 変えたとき波及しそうな箇所
- **優先度**: High / Medium / Low + 一言根拠

**優先度の決め方**:

| 優先度 | 目安 |
| --- | --- |
| High | 規約違反（`any` / Non-null `!` / `enum` 等） / セキュリティリスク / バリデーション漏れ / 明確な SRP 違反でテストできていない箇所 |
| Medium | DRY 違反でコピペが 3 箇所以上 / 50 行を大きく超える関数 / `lib/` に切り出すべき純粋ロジックが routes に貼り付いている |
| Low | 命名の改善余地 / コメントの「なぜ」不足 / Tailwind の冗長なクラス連結 / 軽微な凝集度向上 |

### Step 3: レポート出力（標準出力 = 会話本文）

レポートは **会話本文に Markdown で出力** する（ファイル化しない）。長さは指摘数に応じて伸縮するが、**サマリーを冒頭に置く** ことで読み始めの摩擦を下げる。

#### レポートのテンプレート

```markdown
# リファクタリングレビュー結果

## 対象
- 対象: <ファイル / ディレクトリ / 範囲>
- ベースライン: テスト緑（YYYY-MM-DD HH:MM 時点）/ または「未確認」
- 規約参照: AGENTS.md / .kiro/steering/code-conventions.md

## サマリー
- 指摘件数: High <件> / Medium <件> / Low <件>
- 最重要トピック: <1〜3 行でハイライト>
- 全体所感: <2〜4 行。良い点も書く>

## 指摘一覧

### [High] #1 <タイトル>
- **観点**: SOLID-S（単一責任原則 = 1ファイルは1つの責務だけ持つべき）
- **対象**: `app/src/routes/expense.ts:42-130`
- **現状**: ルートハンドラ内に「JSON パース → バリデーション → DB 書き込み → 集計ロジック → HTML レンダリング」が全て直書きされている。
- **問題**: 集計ロジックを別画面でも使いたい / 集計のテストを書きたいときに、ルート全体をモックする必要があって辛い。仕様変更時の影響範囲も広がる。
- **リファクタリング案**:
  - 集計ロジックを `app/src/lib/expense-summary.ts` に切り出し、純粋関数として export
  - ルートハンドラはバリデーション後の値を渡して結果を受け取るだけにする
- **影響範囲**: `routes/expense.ts` / 新規 `lib/expense-summary.ts` / 新規 `tests/lib/expense-summary.test.ts`
- **既存テストへの影響**: なし（ルートテストはそのまま通る想定）

### [Medium] #2 <タイトル>
...

### [Low] #N <タイトル>
...

## 規約準拠チェック
- [ ] `any` 使用: <なし / あり: 箇所>
- [ ] Non-null assertion `!`: <なし / あり>
- [ ] `@ts-ignore`: <なし / あり>
- [ ] `enum`: <なし / あり>
- [ ] export 関数の戻り値型明示: <すべて明示 / 漏れ: 箇所>
- [ ] 外部入力の Zod バリデーション: <網羅 / 漏れ: 箇所>
- [ ] ディレクトリ配置: <準拠 / 逸脱: 箇所>

## SQuaRE 品質特性スコア（主観 5 段階）
| カテゴリ | 主なサブ特性 | スコア | 一言 |
| --- | --- | --- | --- |
| 保守性 | モジュール性 / 再利用性 / 解析性 / 修正性 / 試験性 | 2 / 5 | 純粋ロジックの切り出し不足 |
| 信頼性 | 障害許容性 / 回復性 | 4 / 5 | エラー処理は概ね妥当 |
| セキュリティ | 機密性 / 完全性 | 4 / 5 | 入力検証あり。CSP は要検討 |
| 性能効率性 | 時間効率性 | 4 / 5 | 明らかな悪化点なし |
| 使用性 | 学習容易性 | - | スコープ外 |

> スコアは主観の目安です。比較しやすくするためのもので、絶対評価ではありません。

## 次のアクション提案
- 仕様書化して [[spec-implementing]] で着手するなら、High → Medium の順で対応するのが安全です。
- Low はまとめて 1 件の仕様書にしても良いと思います。
- **仕様書化を希望する場合**は「仕様書を書いて」「リファクタ仕様書をお願い」とお伝えください。
- まずは特定の指摘について深掘りしたい場合は、「#3 を詳しく」のように番号で指定してください。
```

レポート出力後、**必ず一度応答を終え、ユーザーの次の指示を待つ**。仕様書化やコード修正には自動で進まない。

### Step 4: 仕様書化の希望確認（任意・ユーザー駆動）

ユーザーが「仕様書を書いて」「リファクタ仕様書をお願い」等と指示したら、`AskUserQuestion` で以下を確定する:

1. **対象とする指摘**: 「全件」/「High のみ」/「番号指定（#1, #3, #5 等）」
2. **feature 名**: `refactor-<対象>` 形式の候補を提示（例: `refactor-expense-route`, `refactor-summary-lib`）。複数の関心事を 1 つの仕様にまとめると着手しづらくなるので、テーマが分かれるなら **feature を分けることを提案** する
3. **既存 feature への追記か新規作成か**: 該当 feature が既にあれば追記、無ければ新規作成

確定後、**`app/specs/<feature-name>/` 配下にリファクタリング仕様書を生成** する。

> 仕様書の **構成・テンプレート・出力場所のフォーマットだけ** を [[updating]] から借用する（As-is → To-be → 影響範囲 → 回帰テスト → 手順、という既存コード変更向けの型がそのまま使えるため）。ただしリファクタリングの仕様化そのものは本スキルの責務であり、[[updating]] には回さない（[[updating]] は「振る舞いが変わる変更」専用）。

### Step 5: 仕様書の生成

`app/specs/<feature-name>/` 配下に以下を生成する（[[updating]] の構成と同一）:

```
app/specs/<feature-name>/
├── 00-overview.md            # リファクタリングの動機・対象範囲・関連指摘
├── 01-current-state.md       # 現状（As-is）: 該当コードの構造と問題点
├── 02-changes.md             # 変更内容（To-be）: リファクタ後の構造
├── 03-impact-regression.md   # 影響範囲・回帰テスト計画（**振る舞いを変えない** が肝）
└── 04-implementation-plan.md # 段階的な実装手順（小さな単位で進める）
```

リファクタリング仕様書ならではの注意点を、各ファイルに **必ず織り込む**:

#### 00-overview.md で特に書くこと
- **変更種別**: 「内部リファクタリング（外部から見た振る舞いは変えない）」と明記
- **影響範囲**: ユーザー操作・URL・API レスポンス形式・データ形式は **変わらない** ことを明記
- **動機**: レビューで指摘された具体的な問題（番号で参照）
- **完成の定義**: 既存テスト全件成功・カバレッジ維持・結合テスト既存シナリオ通過 を強調

#### 01-current-state.md で特に書くこと
- レビュー指摘 #X〜#Y の **現状記述をそのまま転記**
- 該当コードの構造図（簡易な箇条書きで十分）
- 現状の責務の境界が曖昧な箇所

#### 02-changes.md で特に書くこと
- リファクタ **後の構造** を明示（新規ファイル / 移動するロジック / 残るファイル）
- **公開 API（関数シグネチャ / 型）の変更有無**: 原則「変更なし」を貫く。やむを得ない場合は明示
- リファクタ案ごとに「採用案」と「却下した別案 + 理由」があれば残す

#### 03-impact-regression.md で特に書くこと
- **「振る舞いが変わっていないこと」を保証するテスト観点** を最優先で書く
- 既存テストのうち **絶対に落とせないもの** をリストアップ
- 既存テストがカバーしていない範囲（カバレッジ不足）があれば、**リファクタ前に「特性テスト」を追加する** ことを提案
  - 特性テスト = 現状の振る舞いを記録するためのテスト。リファクタの safety net
- 性能特性が変わる可能性がある場合（明らかなアルゴリズム変更等）はその旨

#### 04-implementation-plan.md で特に書くこと
- **小さな単位（1 ステップごとにテストで確認できる粒度）** に分割する
- 各ステップで「テストグリーン維持」を明示
- 推奨フェーズ例:
  - Phase 1: 既存テストの実行 + 特性テスト追加（safety net 強化）
  - Phase 2: 純粋ロジックの切り出し（最も安全）
  - Phase 3: 呼び出し元の差し替え（型エラー駆動で進める）
  - Phase 4: 不要になったコード削除 + 命名整理
  - Phase 5: 全テスト（単体 + 結合）+ Biome check（`npm run lint`。`npx biome` は使わない）の最終確認

### Step 6: 生成後のサマリーと次のアクション

ファイル生成完了後、以下を **3〜5 行で** サマリーする:

- 生成したファイル一覧
- 読み進める推奨順序（00 → 01 → 02 → 03 → 04）
- **特に注意すべきポイント**（振る舞いを変えない / 既存テスト維持 / 特性テスト追加の要否）
- 仕様書のレビュー・調整が終わったら「実装を開始して」と伝えれば [[spec-implementing]] で実装に進める旨

**重要: ここで必ず一度応答を終え、ユーザーからの次の指示を待つ。**
仕様書を生成しただけで実装には絶対に着手しない。

### Step 7: 対話で詰める（実装には進まない）

ユーザーから追加要望が来たら、影響範囲を一言示してから該当ファイルを `Edit` で更新する。複数ファイルに波及する変更（例: To-be の方針変更）は **すべて一貫性を保ったまま** 更新する。

このステップでもユーザーが明示的に実装着手を指示するまでは、仕様書の更新のみに留める。

## 出力ルール

- ユーザーへの説明は **必ず日本語**で、簡潔に
- 専門用語の初出時は **1 行で噛み砕いて補足**（例: 「SRP（単一責任原則 = 1つのクラスは1つの責務だけ持つべき）」）
- レビューレポートは **会話本文に Markdown で出力**。ファイル化しない
- 仕様書を生成したら、生成ファイルと変更点の要約を 3〜5 行で報告して **応答を終了**
- ユーザーが「実装に着手してよい」と明示的に言うまでは実装に進まない
- 良い点も書く（指摘ばかりだとモチベーションが下がる）

## やってはいけないこと

- **コードを直接書き換えること**（このスキルの責務は「レビュー出力」と「希望時の仕様書生成」まで）
- **振る舞いを変える提案を「リファクタリング」として提案すること**（バグ修正・機能追加は別タスク扱い）
- **既存テストが赤いままリファクタリング提案を組むこと**（先にテスト失敗を直す旨を強調）
- **「将来こうなるかも」だけを根拠に抽象化を提案すること**（KISS の自己適用）
- **3 箇所未満の重複を DRY 違反として High 扱いすること**（過剰な抽象化を生む）
- **Hono 単体構成を崩す提案をすること**（React / Next.js / Vue 等の導入提案禁止）
- **有料 API / 課金サービスを前提とする提案をすること**
- **生成した仕様書の流れでそのまま実装に着手すること**（実装は [[spec-implementing]] が担う）
- **指摘の根拠なしに優先度 High を乱発すること**（High はノイズになると価値が落ちる）
- **SQuaRE スコアを絶対評価のように提示すること**（あくまで主観の目安と明記）
