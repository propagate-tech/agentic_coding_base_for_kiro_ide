# updating skill

## このスキルが目指すゴール

**既存の `app/` 配下の実装に対する機能修正・機能追加・バグ修正**について、Claude Code がそのまま着手できる粒度の仕様書群を `app/specs/<feature-name>/` 配下に生成する。

[[spec-writing]] が「ゼロからの新規実装」を対象にするのに対し、本スキルは「すでに動いているコードの **振る舞いを変える**（直す・足す）」状況を対象とする。差分（As-is → To-be）・影響範囲・既存機能への波及・回帰テストを明示的に整理することで、**意図せず既存機能を壊すリスクを下げる**ことが最大の狙い。

> **リファクタリングは本スキルの対象外。** 「外から見た振る舞いは変えずに内部構造だけ整理する」依頼（重複の解消・命名整理・責務分割など）は [[refactoring]] が担当する。本スキルは「振る舞いが変わる変更」に集中する。判断に迷う依頼（例: パフォーマンス改善で出力も変わる）が来たら、どちらの性質が主かをユーザーに 1 行で確認してから進める。

> **修正イメージが固まっていないまま発動しても OK。** 「何か良くしたい」「何を足せばいいか分からない」のような曖昧な状態で呼ばれた場合は、いきなり仕様書化せず、既存コードの実態を踏まえた **改善案の提案・壁打ち** から始める（詳細は Step 0.5）。

## 想定ユーザー

- ビジネスパーソン、または初学者エンジニア
- 既存コードの全体像をまだ把握しきっていない可能性がある
- 専門用語を使うときは1行で噛み砕いて補足する
- 「なぜこの修正をするのか」「何を壊さないように気をつけるべきか」を要所で1行添える

## 絶対に守る制約

[[spec-writing]] の制約をそのまま継承する。修正・機能追加の過程で制約を緩めてはいけない。

> **コマンド実行の前提**: 本スキルのチェックリストに現れる `npm test` / `npm run dev` などは、すべて **runtime 配下**（`runtime/node/bin`、Windows は `runtime\node`）の npm を使う。グローバルの node/npm は無い前提。実行時は PATH に runtime の bin を付与する（詳細は [AGENTS.md](../../../AGENTS.md) の「実行環境（Node.js / npm / npx）」）。**Windows では `npm` / `npx` を裸で書かず `npm.cmd` / `npx.cmd` とする**（裸だと `npm.ps1` に解決され ExecutionPolicy で失敗する）。

### 1. 技術スタック
- **Hono 単体のフルスタック構成 (TypeScript)** を前提に既存実装が組まれているはず
  - 修正後もこの構成を崩さない
  - スタイリングは **Tailwind CSS (CDN版)** を踏襲する。既存が未採用なら新規導入可（CDN なのでビルド工程不要）
  - **React / Next.js / Vue / Svelte などのフロントエンドフレームワークを新規導入しない**
- データストアは既存のもの（ファイル / SQLite / インメモリ）を尊重する。データストア変更を伴う修正は必ずユーザーに確認

### 2. 外部サービス・API
- **有料 API・課金サービスを仕様書に組み込まない**
- 既存で使っている外部リソースを変更・置き換える場合は、必ずユーザーに確認
- 無料外部リソースを新規追加する場合は **「個人の自己責任で利用するものとする」** を概要書に必ず明記

### 3. テスト（TDD 順守 + 回帰防止）
- steering（`.kiro/steering/testing-unit-patterns.md`）の通り **TDD を遵守する**
- 各仕様書には必ず以下2種のテスト観点セクションを設ける
  - **新規追加・修正部分のテスト観点**: 今回の変更箇所が正しく動くこと
  - **回帰テスト観点**: 今回の変更で **既存機能が壊れていないこと**
- テストカバレッジは最低 10% を維持。既存テストが落ちる変更を入れる場合は、原因と対処方針を仕様書に明記

### 4. セキュリティ
- 入力バリデーション、XSS、CSRF、シークレット管理など、Hono 構成で関連する観点は **修正箇所ごとに再確認**
- **既存のセキュリティ対策（バリデーション・エスケープ等）を不用意に外す変更**を含まないか必ずチェック

### 5. 後方互換性
- 既存データ・既存 URL・既存 API レスポンス形式を変更する場合、**マイグレーション戦略・互換性の扱い**を仕様書に明記
- 破壊的変更（Breaking Change）は必ずユーザーに確認してから仕様書化する

## 対話フロー

### Step 0: 入力の特定と既存コードの調査

このスキルへの入力（対象 `<feature-name>` または `scope.md` のパス）は、以下の優先順位で決定する:

#### 0-1. 引数で受け取った場合（最優先）

スキル呼び出し時に引数が渡されている場合は、それを最優先で解釈する:

- 引数が `<feature-name>` の場合（例: `add-csv-export`）
  - `app/specs/<feature-name>/` を対象ディレクトリとする
  - 配下に `scope.md` があれば `Read` で読み込み、入り口 A として扱う
  - 配下に `scope.md` が無くてもディレクトリ自体は使う（入り口 B 相当として新規仕様書を生成）
- 引数が `app/specs/<feature-name>/scope.md` 等のパスの場合
  - そのファイルを `Read` で読み込み、親ディレクトリを対象ディレクトリとする
- 引数で指定されたディレクトリ / ファイルが存在しない場合は、ユーザーに「新規作成してよいか」を `AskUserQuestion` で確認

> 引数で明示的に対象が指定されているときは、複数候補があってもユーザーに選び直させない（指定を尊重する）。

#### 0-2. 引数がない場合: `app/specs/*/scope.md` の状況で分岐

`app/specs/` 配下を `Bash` (`ls` 等) で確認し、以下のパターンで対応する:

- **パターン①: `app/specs/*/scope.md` が複数存在**
  - `AskUserQuestion` で「どの scope を起点にするか」を選ばせる
  - 「いずれも使わず新規 feature を作る」も選択肢に含める
- **パターン②: `app/specs/*/scope.md` が1つだけ存在**
  - `AskUserQuestion` で「この `<feature-name>/scope.md` を起点にしてよいか? それとも新規 feature を作るか?」を確認
  - 自動で採用しない（既存の scope と無関係な修正依頼が来る可能性があるため）
- **パターン③: `app/specs/*/scope.md` が1つも存在しない**
  - `AskUserQuestion` で `<feature-name>` を尋ねる（kebab-case の候補を提案）
    - 例: 「集計画面に CSV エクスポートを足す」→ `add-csv-export`
  - 確定したら `app/specs/<feature-name>/` を **新規作成する**
  - この場合 `scope.md` は作らない（このスキルでは `scope.md` を生成しない。必要なら [[scope-planning]] を先に通すよう案内）

#### 0-3. 後方互換

旧パスの `docs/scope.md` しか存在しないときは、ユーザーに「`app/specs/<feature-name>/scope.md` への移動を提案」してから読み込む。

#### 0-4. 入り口の整理

上記の結果として、このスキルは内部的に **2 通りの入り口** に集約される:

- **入り口 A**: `scope.md` を読み込んで、それを起点に仕様書群を生成する
- **入り口 B**: `scope.md` なしで、ユーザーの直接依頼を起点に仕様書群を生成する

どちらに分岐したかをユーザーに 1 行で伝えてから次へ進む（例: 「入り口 A: `app/specs/add-csv-export/scope.md` を起点にします」）。

そのうえで **必ず既存コードを調査** する:

1. **現状のディレクトリ構成把握**: `app/` 配下のトップレベル構造を `Bash` (`ls`/`find`) で確認
2. **修正対象の特定**: 依頼内容に関連しそうなファイルを `Grep` / `Read` で特定
   - データモデル: `app/src/models/`
   - API ルート: `app/src/routes/` / `app/src/index.ts`
   - ビュー: `app/src/views/`
   - 既存テスト: `app/tests/`（結合テストは `app/tests/integration/`）
3. **既存 README / AGENTS.md 関連** に修正対象機能の記載がないか確認
4. **既存仕様書のアーカイブ確認**: `app/specs/archive/` 配下に該当機能の過去仕様があるか確認（あれば設計意図を踏襲）

> 既存コードの調査範囲が広くなる場合は `Agent` (subagent_type=Explore) を併用してよい。ただし、調査結果は仕様書に **As-is として明示的に記録** する。

### Step 0.5: 修正イメージが曖昧なときは提案・壁打ちする

ユーザーが **具体的な機能追加・修正のイメージを持たないまま** このスキルを発動するケースがある（例:「このアプリ何か良くしたい」「改善したいけど何をすればいいか分からない」「とりあえず機能を足したい」）。この場合、いきなり Step 1 で詳細を質問しても答えられないため、**先に提案・壁打ちを行ってから** 変更内容を固める。

#### この分岐に入る判断

以下のいずれかに当てはまるときは、Step 1 に進む前にこの提案フェーズを挟む:

- 依頼に **具体的な変更対象・変更内容が含まれていない**（「改善したい」「良くしたい」「何か足したい」止まり）
- 変更したい方向性はあるが **具体策が決まっていない**（「使いやすくしたい」「もっと便利に」など抽象的）
- ユーザー自身が「何ができるか提案してほしい」「相談したい」と言っている

> 逆に、依頼時点で変更内容が具体的（「CSV エクスポートを足したい」「この 400 エラーを直したい」等）なら、この Step 0.5 は飛ばして Step 1 へ進む。

#### 提案の作り方（As-is 調査を根拠にする）

Step 0 で把握した **既存コードの実態（As-is）を根拠に**、地に足のついた改善案を出す。憶測で「一般論」を並べない。

1. 既存実装を見て気づいた **改善余地・不足機能・小さな不便** を拾う
   - 例: 入力フォームにバリデーションがない / 一覧に検索や並び替えがない / エラー時の表示が不親切 / よく使う操作に導線がない
2. **3〜4 個の改善案** を、初学者にも価値が伝わる粒度で用意する。各案に以下を 1 行ずつ添える:
   - **何ができるようになるか**（ユーザー目線の価値）
   - **ざっくりの規模感**（小さくすぐできる / そこそこ / 大きめ）
   - **種別**（機能追加 / バグ修正 / 使い勝手の改善 など）
3. 制約（Hono 単体・無料リソースのみ・30分〜1時間で実装できる粒度）を満たす案を優先する。大きすぎる案は「分割すると最初の一歩はこれ」と添える。

#### 提案の出し方

- `AskUserQuestion` で **3〜4 案を選択肢として提示**する。各選択肢に「何が嬉しいか」を 1 行で書く
- 「どれもピンと来ない / 自分の案を試したい」も拾えるよう、選択肢には頼り切らず、**本文側でも箇条書きで案を見せて自由入力も歓迎する**旨を伝える
- ユーザーが案を選んだら、その方向で **軽く壁打ち**（「具体的にはこういう挙動を想定していますか?」を 1〜2 往復）して輪郭を掴む
- 1〜2 往復で方向性が固まったら、**Step 1 に合流**して残りの不足情報をまとめて確認する

> このフェーズはあくまで「変更内容を一緒に決める」ための対話。**ここで仕様書を書き始めたり実装したりしない**。方向性が決まってから Step 1 → Step 2 へ進む。

### Step 1: 不足情報の洗い出しと一括確認

既存システムへの変更で、特に確認が必要な観点:

- **修正の動機 / トリガー**: バグ修正 / 機能追加 / 仕様変更 / パフォーマンス改善 / セキュリティ対応（※純粋なリファクタリングは [[refactoring]] に回す）
- **影響を許容できる範囲**: 既存ユーザー操作を壊してよいか / URL や API 形式を変更してよいか
- **データ移行の要否**: 既存データの形式が変わるなら移行スクリプトの要否
- **後方互換性の要件**: 旧クライアント / 旧 URL を一定期間維持するか
- **段階的リリースの要否**: 一気に切り替えるか / フィーチャーフラグ等で段階的にするか
- **回帰テストの優先範囲**: 修正箇所の周辺で必ず守りたい既存挙動

不足項目を **まとめて1つの `AskUserQuestion`** で確認する（1問1答で往復させない）。**3〜5項目に絞り**、決められない部分は「**初学者向けのおすすめ案**」を添えて選択肢化する。

例:
- 「既存の `/api/expense` の JSON 形式を変更してもよいですか? (A) 変更可（破壊的変更） / (B) 新フィールドを追加するのみ / (C) 新エンドポイント `/api/v2/expense` を追加」
- 「データ移行は? (A) 不要 / (B) 起動時に自動移行 / (C) 別途スクリプトで手動移行」

### Step 2: 仕様書群の生成

`<feature-name>` は Step 0 で決めたもの（scope.md 由来 or ユーザー回答由来）を使う。

`app/specs/<feature-name>/` 配下に以下の構成で **一気に** ファイルを生成する（既存の `scope.md` には触れない）:

```
app/specs/<feature-name>/
├── scope.md                  # [[scope-planning]] が作成済みなら存在（このスキルでは編集しない）
├── 00-overview.md            # 修正の動機・影響範囲全体像・関連 US
├── 01-current-state.md       # 現状（As-is）の整理: 既存コード・データ・挙動
├── 02-changes.md             # 変更内容（To-be）と差分: 何を、どこで、どう変えるか
├── 03-impact-regression.md   # 影響範囲分析・回帰テスト計画
└── 04-implementation-plan.md # 段階的な実装手順（パッチ単位 + 動作確認）
```

既に `00-overview.md` などが存在する場合は、上書きするかをユーザーに確認する。

各ファイルの先頭には **このファイルの位置づけ** と **依存関係** を明示する。例:

```markdown
> **このファイルの位置づけ**: 変更内容（To-be）
> **依存**: [[01-current-state]] を読んでから着手
> **次に読むもの**: [[03-impact-regression]] で影響範囲を確認
```

### Step 3: 生成後のサマリーと次のアクション

ファイル生成完了後、以下を **3〜5 行で** サマリーする:

- 生成したファイル一覧
- **読み進める順序の推奨**（00 → 01 → 02 → 03 → 04）
- **特に注意すべき既存機能への影響**（Step 0 の調査で見えたもの）
- 仕様書を読んで気になる点があれば対話で詰める旨
- **このスキルはここで終了する旨**（実装には自動で進まない）

例:
```
app/specs/add-csv-export/ に5ファイル生成しました。
読み進める推奨順序: 00 → 01 → 02 → 03 → 04
既存機能への影響は 03-impact-regression.md に整理しました。
特に GET /api/expense のレスポンス形式変更を含むため、フロントエンド側の既存表示への影響に注意してください。
仕様書のレビュー・調整が終わって実装に進む準備ができたら、改めて「実装を開始して」とお伝えください。
```

**重要: ここで必ず一度応答を終え、ユーザーからの次の指示を待つ。**
仕様書を生成しただけで実装には絶対に着手しない。ユーザーが明示的に「実装に着手してよい」「実装を開始して」等と指示するまでは、コード生成・既存ファイル編集（仕様書以外）・依存関係のインストール等の実装行為を一切行わない。

### Step 4: 対話で詰める（実装には進まない）

ユーザーから追加要望・変更要望が来たら、影響範囲を一言で示してから該当ファイルを `Edit` で更新する。変更が複数ファイルに波及する場合（例: To-be が変わると影響範囲も変わる）は、関連ファイルを **すべて** 一貫性を保ったまま更新する。

このステップでもユーザーが明示的に実装着手を指示するまでは、仕様書の更新のみに留め、実装に進まない。

## 6. 技術スタック（全体共通・既存踏襲）
- **フレームワーク**: Hono (TypeScript) — 既存構成を維持
- **ビュー**: Hono JSX
- **スタイリング**: Tailwind CSS (CDN版) を踏襲 / 既存が未採用なら新規導入可（ビルド不要）
- **データ保存**: <既存の方式を踏襲 / 変更する場合はその旨と理由>
- **テスト**: Vitest（単体 + Hono `app.request()` による結合テスト）— 既存テストを必ず維持

## 出力ルール

- ユーザーへの説明は **必ず日本語**で、簡潔に
- 修正イメージが曖昧なまま発動したときは、Step 0.5 で **既存コードを根拠にした改善案を提案・壁打ち** してから変更内容を固める（憶測の一般論を並べない）
- 専門用語の初出時はカッコ書きで補足
- 既存コード調査の段階で発見した重要事項は **As-is として 01-current-state.md に必ず記録**
- ファイル生成中は進捗を 1〜2 行で報告（例: 「02-changes.md を生成中...」）
- 全ファイル生成後、Step 3 のサマリーを出して **応答を終了する**
- `scope.md` が存在する場合、その文言を **改変しない**。仕様書側で詳細化する
- 仕様書を更新したら、変更点と影響範囲を 1〜3 行で要約報告
- ユーザーが「実装に着手してよい」と明示的に言うまでは Step 4 のループに留まり、実装には進まない

## やってはいけないこと

- 純粋なリファクタリング（振る舞いを変えずに内部構造だけ整理する依頼）をこのスキルで仕様書化すること（[[refactoring]] に案内する。本スキルは「振る舞いが変わる変更」専用）
- 既存コードを調査せずに仕様書を書き始めること（憶測で As-is を埋めない）
- 1ファイルにすべての差分を詰め込むこと（As-is / To-be / 影響範囲 / 手順 を分けて書く）
- 既存機能への影響評価を省略すること（**回帰防止が本スキルの最大の存在意義**）
- 破壊的変更をユーザー確認なしに仕様書化すること
- 既存のセキュリティ対策（バリデーション・エスケープ等）を外す変更を黙って入れること
- 有料 API / 課金サービスを仕様書に組み込むこと
- React / Next.js など Hono 単体構成を破る代替案を出すこと
- ユーザーストーリーや受け入れ基準を省略すること
- テスト観点（特に **回帰テスト**）を省略すること（steering の TDD 遵守と矛盾する）
- 「個人の自己責任で利用する」文言（外部リソース使用時）を省略すること
- **仕様書を生成した流れでそのまま実装に着手すること**（Auto Mode であってもこのスキルの責務は仕様書作成までで、実装はユーザーの明示的な指示を待つ）
- **仕様書生成完了後に `app/src/` 配下のコード編集・依存パッケージの追加・テスト実行などの実装行為を行うこと**
