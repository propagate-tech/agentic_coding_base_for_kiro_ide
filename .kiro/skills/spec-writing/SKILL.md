# spec-writing skill

## このスキルが目指すゴール

`app/specs/<feature-name>/scope.md`（[[scope-planning]] の成果物）を読み込み、**Claude Code がそのまま実装に取りかかれる粒度の仕様書群**を **同じ** `app/specs/<feature-name>/` 配下に生成する。

スコープと仕様書を同一ディレクトリに集約することで、参照・更新・アーカイブの単位を揃える。

仕様書は **並列実装可能な単位**（データモデル / バックエンド API / フロントエンド ビュー / 統合手順）に分割し、各ファイルに「ユーザーストーリー」「受け入れ基準」「テスト観点」「実装手順（順序付きタスク）」を盛り込む。

## 想定ユーザー

- ビジネスパーソン、または初学者エンジニア
- 専門用語を使うときは1行で噛み砕いて補足する
- 「なぜこの仕様にしているのか」を要所で1行添える

## 絶対に守る制約

[[scope-planning]] の制約をそのまま継承する。仕様書化の過程で制約を緩めてはいけない。

### 1. 技術スタック
- **Hono 単体のフルスタック構成 (TypeScript)** が前提
  - サーバー / ビュー / ルーティングはすべて Hono
  - ビューは Hono JSX (サーバーサイドレンダリング)
  - スタイリングは **Tailwind CSS (CDN版)** を Layout の `<head>` で読み込む（ビルド不要）
  - クライアント JS は最小限の vanilla JS / htmx のみ
  - **React / Next.js / Vue / Svelte などのフロントエンドフレームワークは絶対に提案しない**
- データストアは **ファイル / SQLite / インメモリ** を優先

### 2. 外部サービス・API
- **有料 API・課金サービスを仕様書に組み込まない**
- 無料外部リソースを使う場合は **「個人の自己責任で利用するものとする」** を概要書に必ず明記
- scope.md に書かれた外部リソースを変更する場合は、必ずユーザーに確認

### 3. テスト
- このプロジェクトは **TDD を遵守する**（`.kiro/steering/testing-unit-patterns.md` 参照）
- 各仕様書には必ず **テスト観点** セクションを設ける
  - バックエンド系: Vitest による単体テスト観点
  - フロントエンド系: Hono `app.request()` による結合テスト観点（Playwright 等ブラウザ E2E は使わない）
- テストカバレッジ目標 10% 以上 を満たせる粒度のテスト観点を書く

### 4. セキュリティ
- 入力バリデーション、XSS、CSRF、シークレット管理など、Hono 構成で関連する観点は **各仕様書に明記**
- 「セキュリティ上問題ないか」を初学者でも判断できるよう、対処方針まで書く

## 対話フロー

### Step 0: scope.md の読み込み

1. `app/specs/` 配下を確認し、対象の `<feature-name>/scope.md` を特定
   - `app/specs/*/scope.md` が1つも見つからなければ「[[scope-planning]] skill を先に実行してください」と案内して終了
   - 複数 `app/specs/*/scope.md` がある場合は、どれを使うかユーザーに `AskUserQuestion` で選ばせる
   - 後方互換: 旧パスの `docs/scope.md` しか存在しないときは、ユーザーに「`app/specs/<feature-name>/scope.md` への移動を提案」してから読み込む
2. `Read` で内容を取得し、以下を抽出
   - タイトル / 課題 / 解決策
   - 採用アプローチ / コア機能
   - 技術スタック / 外部データ
   - 完成の定義 / 実装時間内訳
   - スコープ外項目
3. 仕様書群の出力先は **scope.md と同じディレクトリ** (`app/specs/<feature-name>/`)。`<feature-name>` を別途決め直さない。

### Step 1: 不足情報の洗い出しと一括確認

scope.md には「実装に必要な細部」が抜けていることが多い。以下を **チェックリスト** にして照合する:

- **データモデル**: 何のデータをどの形で保存するか（フィールド名・型・必須/任意・初期値）
- **API エンドポイント**: HTTP メソッド・パス・リクエスト/レスポンス形式
- **画面構成**: 画面の数・各画面の URL・遷移パターン
- **入力バリデーション**: 必須項目・形式チェック・エラー時の表示
- **エラーハンドリング**: 通信エラー・データなし・予期せぬ状態
- **永続化の挙動**: アプリ再起動時のデータ保持、リセット手段
- **認証/認可**: 必要か、その場合の手段
- **国際化/タイムゾーン**: 日本語のみか、日時の扱い

不足項目を **まとめて1つの `AskUserQuestion`** で確認する（1問1答で往復させない）。**3〜5項目程度に絞り**、決められない部分は「**初学者向けのおすすめ案**」を添えて選択肢化する。

**必ず「すべておすすめ案でおまかせ（推奨）」を先頭の選択肢に置く**こと。細部の判断に迷う受講者を1タップで先へ進められるようにするため。おまかせが選ばれたら、各項目のおすすめ案を採用した旨を1行ずつ示してから Step 2 へ進む。

例:
- 「細部の決め方は? (A) すべておすすめ案でおまかせ（推奨） / (B) 個別に決めたい」
- 個別に決める場合: 「データはどう保存しますか? (A) JSON ファイル（おすすめ） / (B) SQLite / (C) ブラウザのみ」

### Step 2: 仕様書群の生成

`<feature-name>` は **scope.md があるディレクトリ名をそのまま使う** (`app/specs/<feature-name>/scope.md` → `<feature-name>`)。新たに kebab-case を作り直さない。

同じディレクトリに以下の構成で **一気に** ファイルを生成する（`scope.md` には触れない）:

```
app/specs/<feature-name>/
├── scope.md                # [[scope-planning]] が作成済み（このスキルでは編集しない）
├── 00-overview.md          # 全体像・ユーザーストーリー一覧・共通要件
├── 01-data-model.md        # データモデル（他の全ファイルが依存する基盤）
├── 02-backend-api.md       # Hono ルーティング・API 仕様（バックエンド並列単位）
├── 03-frontend-view.md     # Hono JSX 画面・UI 仕様（フロントエンド並列単位）
└── 04-integration.md       # 実装順序・統合手順・動作確認手順
```

既に `00-overview.md` などが存在する場合は、上書きするかをユーザーに確認する。

各ファイルの先頭には **このファイルの位置づけ** と **依存関係** を明示する。例:

```markdown
> **このファイルの位置づけ**: バックエンド並列単位
> **依存**: [[01-data-model]] を先に実装してください
> **並列可能**: [[03-frontend-view]] と同時に着手できます
```

### Step 3: 生成後のサマリーと次のアクション

ファイル生成完了後、以下を **3〜5 行で** サマリーする:

- 生成したファイル一覧
- **実装着手順序の推奨**（並列着手可能なペアも明示）
- 仕様書を読んで気になる点があれば対話で詰める旨
- **このスキルはここで終了する旨**（実装には自動で進まない）

例:
```
app/specs/expense-tracker/ に5ファイル生成しました。
着手順序の推奨:
1. 01-data-model.md（最初に実装。他の基盤）
2. 02-backend-api.md と 03-frontend-view.md は並列着手可能
3. 04-integration.md は両者完成後の最終確認
気になる仕様があれば対話で詰めましょう。
仕様書のレビュー・調整が終わって実装に進む準備ができたら、改めて「実装を開始して」とお伝えください。
```

**重要: ここで必ず一度応答を終え、ユーザーからの次の指示を待つ。**
仕様書を生成しただけで実装には絶対に着手しない。ユーザーが明示的に「実装に着手してよい」「実装を開始して」等と指示するまでは、コード生成・ファイル作成（仕様書以外）・依存関係のインストール等の実装行為を一切行わない。

### Step 4: 対話で詰める（実装には進まない）

ユーザーから追加要望・変更要望が来たら、影響範囲を一言で示してから該当ファイルを `Edit` で更新する。影響するファイルが複数ある場合（例: データモデル変更）は、関連ファイルを **すべて** 一貫性を保ったまま更新する。

このステップでもユーザーが明示的に実装着手を指示するまでは、仕様書の更新のみに留め、実装に進まない。

## 3. ルーティング一覧

| メソッド | パス | 概要 | レスポンス形式 |
| --- | --- | --- | --- |
| GET | `/` | トップページ表示 | HTML (JSX) |
| GET | `/api/<entity>` | 一覧取得 | JSON |
| POST | `/api/<entity>` | 新規作成 | JSON (作成された値) |

## 4. エンドポイント詳細

### POST `/api/<entity>`
**ユーザーストーリー受け入れ基準**:
- **Given**: クライアントが必須フィールド付き JSON を送る
  **When**: POST `/api/<entity>` に送信
  **Then**: 201 Created + 作成済みエンティティ JSON が返る

**リクエスト**:
```json
{
  "amount": 1000,
  "category": "food"
}
```

**正常レスポンス (201)**:
```json
{
  "id": "uuid-xxx",
  "amount": 1000,
  "category": "food",
  "createdAt": "2026-05-25T10:00:00.000Z"
}
```

**エラーレスポンス**:
- 400 Bad Request: バリデーションエラー（`{ "error": "amount must be positive" }`）
- 500 Internal Server Error: 想定外（`{ "error": "internal error" }`）

（同形式で繰り返し）

## 5. セキュリティ要件
- **入力バリデーション**: モデル層のバリデーションを必ず通す。直接データを保存しない
- **CSRF**: フォーム POST には、同一オリジン前提で `SameSite=Lax` Cookie or トークン
- **シークレット**: 環境変数 `.env` で管理（他者と共有・配布しない）
- **エラーメッセージ**: 内部実装の詳細（スタックトレース等）をレスポンスに含めない

## 6. テスト観点（Vitest 単体）
- [ ] 各エンドポイントが期待する HTTP ステータスを返す
- [ ] 正常系で返り値の型・フィールドが仕様通り
- [ ] バリデーションエラーで 400 を返す
- [ ] 存在しない ID で 404 を返す
- [ ] CRUD 一連の流れ（作成→取得→更新→削除）が成立

## 7. 実装手順（順序付きタスク）

## 5. スタイル方針
- **Tailwind CSS (CDN版)** を Layout コンポーネントの `<head>` で読み込む:
  - `<script src="https://cdn.tailwindcss.com"></script>`
  - ビルド工程は不要。JSX 内に `class="..."` を書けばそのまま効く（Hono JSX は `className` ではなく `class` を使う）
- レスポンシブ対応は Tailwind のブレークポイント (`sm:` / `md:` / `lg:`) を使う
- 必要に応じて `meta viewport` を Layout に入れる
- どうしても Tailwind で表現できないスタイルだけ `<style>` タグでインラインに最小限追加

## 6. クライアント JS の方針
- **基本: クライアント JS なし**（フォーム送信 → リダイレクトで完結）
- 必要時: vanilla JS をインラインで（例: 削除確認ダイアログ）
- htmx を使う場合は `<script src="https://unpkg.com/htmx.org">` で読み込み（CDN は自己責任）

## 7. セキュリティ要件
- **XSS**: Hono JSX は自動エスケープされる。`{user_input}` をそのまま埋め込んで OK
- **`dangerouslySetInnerHTML` 系は使わない**
- **CSRF**: フォーム POST は同一オリジン前提で `SameSite=Lax` Cookie
- **外部 CDN**: 利用する場合は SRI（Subresource Integrity）ハッシュを推奨（ただし Tailwind CDN は SRI 非提供のためそのまま読み込む）

## 8. テスト観点（結合テスト: Hono `app.request()`）
**主要ユーザーシナリオ1〜2本に絞る**（ハンズオンの時間内に収めるため。細かい分岐は Vitest 単体テスト側で担保する）:

- [ ] （任意）エラー系: 必須項目を空で POST するとエラーメッセージが返る
