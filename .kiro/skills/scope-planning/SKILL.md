# scope-planning skill

## このスキルが目指すゴール

ユーザーの「課題の一言」「解決策の一言」を出発点に、**実装25〜30分で動くものを作り切れる粒度**まで噛み砕いた `app/specs/<feature-name>/scope.md` を、対話を通じて完成させる。

> **時間の前提**: このハンズオンは全体で約1時間。スコープ決め15分 → 仕様書10分 → 実装25分 → 動作確認10分の配分を想定しているため、**実装スコープは25〜30分に収まる大きさ**に絞り込むことが本スキルの最重要責務。

ただし**ユーザーが「何を作りたいか」を明確に持っていないケースも想定する**。その場合は、いきなりスコープを詰めにいかず、まず**ユーザーの業務や日々の困りごとをヒアリングし、ここで作れそうな題材を複数提案する**ところから始める。題材が決まってから通常のスコープ詰めフローに合流する。

成果物の置き場所は、後段の [[spec-writing]] skill が生成する仕様書群と **同じディレクトリ** (`app/specs/<feature-name>/`) に揃える。これによりスコープと仕様書が常にセットで参照できる。

そのまま Claude Code に渡せば、ユーザーストーリーや機能ベースの仕様書を書き出せる粒度を目標にする。

## 想定ユーザー

- ビジネスパーソン、または初学者エンジニア
- 専門用語を使うときは1行で噛み砕いて補足する
- 「なぜそれを聞いているのか」を毎ステップで一言添える

## 絶対に守る制約

### 1. 技術スタック
- Web アプリは **Hono 単体のフルスタック構成** を原則とする
  - サーバー: Hono (TypeScript)
  - ビュー: Hono JSX または HTML 文字列レンダリング
  - スタイリング: **Tailwind CSS (CDN版)** を Layout の `<head>` で読み込む（ビルド工程不要）
  - クライアント JS が必要なら最小限の vanilla JS / htmx 程度
  - React / Next.js / Vue / Svelte などのフロントエンドフレームワークは原則導入しない
- データストアは **ファイル / SQLite / インメモリ** を優先（無料・ローカル完結）

### 2. 外部サービス・API
- **有料 API・サービスをプロダクトコードから呼び出す実装は絶対に提案しない**
  - クレカ登録・無料トライアル後課金・従量課金が発生するもの全てNG
  - 例: OpenAI API, Anthropic API, Google Maps Platform 有料枠, AWS の課金が走るサービス、など
- 代わりに以下は **OK**:
  - 公的オープンデータ (e-Stat, 気象庁, 国土地理院, RESAS など)
  - 事前計算済みの静的データ (CSV/JSON をリポジトリに同梱)
  - 完全無料の API (キー不要、または無料登録のみで課金リスクなし)
- 無料外部リソースを使う場合は **「個人の自己責任で利用するものとする」を scope.md に必ず明記**
  - 利用規約・レート制限・データの正確性は使う本人が責任を負う旨を1行で書く

### 3. スコープの大きさ
- 完成時間の目安は **実装 25〜30 分** (ハンズオン全体1時間のうち実装に割ける時間)
- これを超えそうな案は「カット候補」を必ず明示する

## 対話フロー

### Step 0: 入力の確認と分岐

skill 起動時の引数（あれば）に課題や解決策のヒントが含まれているかチェックし、**ユーザーが「作りたいもの」のイメージを持っているかどうか**でフローを分岐する。

- **作りたいものが固まっている** (課題・解決策の方向性が言える) → そのまま **Step 0a** へ
- **作りたいものが固まっていない / 「何か作ってみたいけどネタがない」状態** → **Step 0b (ヒアリングと題材提案)** へ

判断に迷う場合や、引数が空・抽象的すぎる (例: 「何か作りたい」だけ) な場合は、まず1問だけ「**作りたいものはもう決まっていますか? それとも一緒に題材から探しますか?**」と確認してから分岐する。**勝手に題材を決め打ちしない**。

#### Step 0a: 課題・解決策が決まっている場合

不足している情報があれば、**まとめて1つの質問で聞く** (1問1答で往復させない)。最低限揃えたいのは以下:

- **課題 (Problem)**: 誰の・どんな困りごとを解きたいか (一言で)
- **解決策の方向性 (Solution)**: どうやって解こうとしているか (一言で)
- **想定ユーザー像**: 自分が使う / 家族友人が使う / 不特定多数 etc.
- **使う場面**: いつ、どこで、何回くらい使うものか

`AskUserQuestion` を使うか、シンプルなテキスト質問として送る。**初学者向けに「例えばこんな粒度でOKです」と例示を1つ添える**。揃ったら Step 1 へ。

#### Step 0b: 作りたいものが固まっていない場合 (ヒアリング → 題材提案)

ここでの目的は **「作りたいものを押し付ける」ことではなく、ユーザーの業務・生活から “ここで作れそうな題材” を一緒に見つけること**。以下の順で進める。

**1. 業務・困りごとのヒアリング**

`AskUserQuestion` などで、**まとめて1〜数問**だけ聞く (尋問にしない)。聞きたい観点の例:

- **普段の業務 / 役割**: どんな仕事をしているか (例: 営業、経理、カスタマーサポート、学生 など)
- **手作業・繰り返し作業**: 毎日・毎週やっている地味で面倒な作業は何か (例: 日報、集計、転記、リマインド)
- **困りごと・「あったらいいな」**: 時間がかかる / ミスりやすい / 覚えきれない、と感じていること
- **扱っているデータ**: Excel / 紙 / メール / 頭の中、など何で管理しているか

**初学者向けに「例えば “毎週月曜にメンバーの予定を集計するのが面倒” みたいな粒度でOKです」と例示を1つ添える**。

**2. ヒアリング結果から題材を3つ前後提案**

聞いた内容をもとに、**この skill の制約 (Hono 単体 / 無料リソースのみ / 実装25〜30分で完成) の中で作れそうな題材を3つ前後**提案する。各題材は以下を1〜2行ずつで簡潔に:

```markdown
### 題材 1: <一言タイトル>
- **どんな困りごとを解くか**: ...
- **作るもの (イメージ)**: ...
- **この制約で作れる理由**: 無料データ / ローカル完結 / 25〜30分で動く 等
```

題材を出すときの注意:
- **業務固有の機密データ・個人情報を扱う前提の題材は避ける** (扱うとしてもダミーデータ / ローカル完結で割り切れるものに寄せる)
- 有料 API・課金サービス・外部送信 (メール送信・SMS 等) が必須になる題材は中心に据えない
- 「実在する社内システムと連携」など、この環境単体で完結しないものは避ける

提案後、`AskUserQuestion` で **3題材 + 「どれもピンと来ない (もう一度ヒアリングし直す)」** の選択肢にして選ばせる。ピンと来ないが選ばれたら、観点を変えて 1. のヒアリングからやり直す。

**3. 題材が決まったら課題・解決策に翻訳**

選ばれた題材を、Step 0a と同じ粒度の **「課題 (Problem)」「解決策の方向性 (Solution)」「想定ユーザー」「利用シーン」** に言い換えてユーザーに1ブロックで提示し、「この理解で合っているか」を確認する。合意できたら Step 1 へ合流する。

### Step 1: 制約と前提のすり合わせ

入力を受け取ったら、**箇条書きで簡潔に**以下を確認・宣言する:

```
受け取った内容:
- 課題: ...
- 解決策の方向性: ...
- 利用シーン: ...

このスキルは以下の前提で進めます:
- Hono 単体のフルスタック構成 (TypeScript)
- 有料 API・課金サービスは使わない (無料データ・無料 API のみ)
- 実装25〜30分で動くものを作り切る粒度に絞る (ハンズオン全体は約1時間)
- 無料外部リソースを使う場合は「個人の自己責任」と明記する

この前提でアプローチ案を3つ出します。
```

ここで `AskUserQuestion` などでブロックせず、宣言したら次の Step に進む。

### Step 2: アプローチ案を3つ提示 (最重要ステップ)

**思いつきの第一案に縛られないことが目的**なので、ここでは必ず明確に性格の異なる3案を出す。各案に以下のラベルのいずれかを付けると初学者にも違いが伝わりやすい:

- **案 A: 最小構成 (まず動く)** — 機能を削りまくって15分前後で動くものを目指す
- **案 B: バランス型 (推奨されやすい中庸)** — 25〜30分で「人に見せられる」最小完成形
- **案 C: 攻め型 (学びが多い)** — 公開オープンデータや新しい技術要素を取り込み、知的好奇心を満たす方向 (40分超になりがちなので、提示時に時間超過リスクを必ず警告する)

ただしテーマによっては「データを変える」「対象ユーザーを変える」「UX を変える」など軸が違う3案にしても良い。**重要なのは「同じテーマの劣化版を3つ並べない」こと**。3案で迷えるくらい毛色を変える。

各案について以下を必ず含める:

```markdown
### 案 A: <ラベル / 一言タイトル>

- **狙い**: この案で何が手に入るか (1〜2行)
- **コア機能**: 必ず作るもの (3つ前後の箇条書き)
- **データ・API**: 何を使うか (具体名 + なぜ無料か)
- **想定実装時間**: 約 X 分 (内訳: ...)
- **できること**: この案で実現できる体験
- **できないこと / 割り切り**: この案では諦める部分
- **技術リスク**: つまずきポイント・難所 (初学者の視点で)
- **セキュリティ / プライバシー上の注意**: 個人情報・スクレイピング・利用規約など
- **向いている人**: どんな目的のユーザーに合うか
```

提示後、`AskUserQuestion` で **「おまかせ (推奨案で即決)」を先頭の選択肢** にした4択にして選ばせる:

1. **おまかせ (推奨)** — このスキルが推す案 (通常は案 B) で即決して先へ進む。迷う受講者を1タップで前進させるための選択肢
2. 案 A / 3. 案 B / 4. 案 C のうち、おまかせの推奨と重複しないもの

組み合わせ希望 (ハイブリッド) は「その他」の自由記述で受け付ける旨を本文に添える。

**3案を出すときの判断基準**:
- 既存サービスのクローン要望でも、無料データで再現可能な領域に絞ったうえで案を出す
- 課金が必要な機能 (決済、メール送信、SMS、地図描画の高負荷、LLM 推論など) を案の中心に据えない
- 認証が必要な案は「ログイン無し / シンプルなパスフレーズ / 公開だが個人特定不可」など、無料で実装できる軽量手段に置き換える

### Step 3: scope.md の初稿を作成

選ばれた案 (またはハイブリッド指示) を元に、`app/specs/<feature-name>/scope.md` を生成する。

- まずスコープのタイトルから **kebab-case の `<feature-name>`** を導出し、ユーザーに「この名前で進めて良いか」を1行で確認
  - 例: 「家計簿アプリ」→ `expense-tracker`、「天気通知bot」→ `weather-notifier`
- ディレクトリ `app/specs/<feature-name>/` が無ければ作成
- 既に `app/specs/<feature-name>/scope.md` が存在する場合は、ユーザーに「上書きする / 別の `<feature-name>` にする」を確認
- 後段の [[spec-writing]] skill が同じディレクトリに `00-overview.md` などを追加する想定で配置する

`scope.md` のテンプレートは下記 [scope.md テンプレート](#scopemd-テンプレート) を使う。

初稿が完成したら、本文に **どこを一緒に詰めていきたいか** を1〜3つ提案する。例:
- 「画面遷移をもう少し具体化しましょうか?」
- 「『完成の定義』が曖昧なので、合格ラインの基準を一緒に決めませんか?」
- 「想定実装時間の内訳が甘いです。機能ごとに分解しますか?」

### Step 4: 対話で調整して完成させる（ダラダラ続けない）

ここからは対話で詰めるが、**ハンズオンでは「初稿 + 1回の調整」で完成扱いにするのを推奨**とする。初稿提示時の「詰めたいポイント」への返答を反映したら、「この内容で完成にして、仕様書作成に進みましょうか?」と **こちらから完成を提案する**。

- ユーザーの追加要望が来たら、影響範囲を一言で示してから `app/specs/<feature-name>/scope.md` を `Edit` で更新する
- 更新するたびに「今ここまで決まっています / まだ詰めきれていない箇所はこれです」と1〜3行で報告する
- 機能が膨らみそうな提案には **必ず「これを入れると実装時間が X 分追加されます。次のどれを削りますか?」と削減候補を一緒に提示する**
- 「やりたいことが膨らんで実装30分を大幅に超えそう」と判断したら、はっきり警告し、Step 2 に戻って案を選び直すことを提案する
- ユーザーがさらに詰めたい意向なら付き合う（強制的に打ち切らない）が、毎回の報告に残り時間への影響を一言添える

## scope.md テンプレート

`app/specs/<feature-name>/scope.md` の初稿は以下の構成で出力する。**初学者でも読めるよう、専門用語にはカッコ書きで補足**を入れる。

````markdown
# スコープ: <タイトル>

> 想定実装時間: 約 X 分 / 作成日: YYYY-MM-DD

## 1. 課題 (Problem)
<誰の何の困りごとを解くか。1〜3行>

## 2. 解決策の方向性 (Solution)
<どうやって解くか。1〜3行>

## 3. 想定ユーザーと利用シーン
- **ユーザー像**: ...
- **利用シーン**: いつ・どこで・何回くらい使うか
- **使うデバイス**: PC / スマホ / 両方

## 4. 採用したアプローチ
**選択した案**: 案 X (<ラベル>)

**選んだ理由**: ...

**捨てた案 (検討した代替)**: 案 Y, 案 Z (簡潔に何を捨てたかメモ)

## 5. スコープに含むもの (In Scope)
今回 25〜30 分で作るもの:
- [ ] ...
- [ ] ...
- [ ] ...

## 6. スコープに含まないもの (Out of Scope)
今回は意図的に作らないもの (将来の課題):
- ...
- ...

## 7. 主要画面・ユーザーフロー
箇条書きで OK:
1. ユーザーが <画面 A> を開く
2. <入力 / 操作> をする
3. システムが <処理> をして <結果> を返す
4. ユーザーは <次のアクション> へ進む

## 8. 技術スタック
- **フレームワーク**: Hono (TypeScript) — サーバー・ビュー・ルーティングを一体で
- **ビュー**: Hono JSX (サーバーサイドレンダリング)
- **スタイリング**: Tailwind CSS (CDN版 `https://cdn.tailwindcss.com`) — ビルド不要
- **データ保存**: <ファイル / SQLite (better-sqlite3) / メモリ / 無し> + 理由
- **クライアント JS**: <無し / vanilla JS 少々 / htmx 等> + 理由
- **実行環境 (ローカル開発)**: Node.js + tsx（同梱の `runtime/node` を使用。ローカル動作のみでデプロイはしない）

> Hono 単体構成を原則とするため、React/Next.js などフロントエンドフレームワークは今回入れません。
> スタイリングは Tailwind CSS の CDN 版を使うのでビルド工程は不要です（外部 CDN 利用は個人の自己責任の範疇）。

## 9. 利用する外部データ / API
すべて無料リソースのみ:
- **<データ名 / API 名>**: <用途> / <無料な理由 (キー不要 / 登録のみ / 公的オープンデータ等)>

> **個人の自己責任で利用するものとする**: 利用規約・レート制限・データの正確性については、利用者本人の責任において確認・遵守する。

## 10. 制約と前提
- 有料 API / 課金が発生するサービスは組み込まない
- 個人情報は <収集しない / ローカル保存のみ / 暗号化など> ※具体的に
- 想定同時利用ユーザー数: <1人 / 数人 / 公開しない>
- 認証: <無し / シンプルなパスフレーズ / その他>

## 11. 技術的リスク・セキュリティ考慮
初学者がつまずきやすい / 注意すべき点:
- **<リスク項目>**: 内容 → 対処方針 (本スコープ内で対処するか、Out of Scope に逃がすか)
- 例: スクレイピング対象サイトの利用規約違反リスク → 公的オープンデータの API 利用に切り替える
- 例: フォーム入力の XSS → Hono JSX の自動エスケープに任せる / `dangerouslySetInnerHTML` 系を使わない
- 例: API キー漏洩 → そもそも有料 API を使わない方針なので低リスク。無料 API のキーも `.env` 管理とし、他者と共有しない。

## 12. 完成の定義 (Definition of Done)
これが満たせれば「完成」と見なす:
- [ ] <ローカルで `npm run dev` でサーバーが立ち上がる>
- [ ] <主要シナリオが手元のブラウザで一通り動く>
- [ ] (任意・時間があれば) <README に最低限の起動方法が書いてある>
- [ ] <Out of Scope を明文化したまま scope.md が残っている>

## 13. 実装時間の内訳 (見積)
| 機能 | 想定時間 |
| --- | --- |
| プロジェクト初期化 (Hono セットアップ) | XX 分 |
| <機能1> | XX 分 |
| <機能2> | XX 分 |
| 動作確認 | XX 分 |
| **合計** | **約 XX 分** |

## 14. 次のステップ
- [ ] この `scope.md` を入力に [[spec-writing]] skill を実行し、同じ `app/specs/<feature-name>/` 配下に仕様書群を生成する
- [ ] 仕様書ができたら、最小機能から実装に着手する
- [ ] 実装開始から20分経過時点で進捗確認 → スコープ削減判断
````

## 出力ルール

- ユーザーへの説明は **必ず日本語**で、簡潔に
- 専門用語の初出時はカッコ書きで補足 (例: 「ルーティング (URL ごとに処理を振り分ける仕組み)」)
- 1メッセージでドカっと全部出さない。Step ごとに区切って対話する
- `app/specs/<feature-name>/scope.md` は `Write` で初稿、以降は `Edit` で差分更新
- 毎回 `scope.md` を更新したら、変更点を 1〜3 行で要約報告する
- 「これは固まりました / これがまだ曖昧です」を明示し、ユーザーに次の判断ポイントを示す
- ハンズオンでは「初稿 + 1回の調整」を目安に、こちらから「完成にして仕様書作成に進みましょうか?」と提案する（ユーザーがさらに詰めたい場合は付き合う）
